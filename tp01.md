# TP01 - Création d'un utilisateur humain Kubernetes avec un certificat X.509

## Objectif

Dans ce TP, nous allons créer un **véritable utilisateur humain** nommé `mohamed` qui pourra se connecter au cluster Kubernetes grâce à un **certificat X.509**.

Contrairement à un **ServiceAccount**, cet utilisateur :

- n'est pas un objet Kubernetes ;
- possède une clé privée et un certificat ;
- utilise `kubectl` depuis son poste de travail ;
- est authentifié par l'API Server grâce à son certificat.

---

# Architecture

```text
                  Kubernetes RBAC

         Utilisateur humain
      (certificat X.509)
               │
               ▼
      kubectl get pods
               │
               ▼
          API Server
               │
      Authentification
        (Certificat)
               │
               ▼
        Utilisateur : mohamed
               │
               ▼
         RoleBinding
               │
               ▼
            Role
```

---

# Étape 1 – Générer la clé privée

Créer une clé RSA de 2048 bits.

```bash
openssl genrsa -out mohamed.key 2048
```

Résultat :

```
mohamed.key
```

Cette clé doit rester privée.

---

# Étape 2 – Générer une CSR (Certificate Signing Request)

Créer une demande de certificat.

```bash
openssl req -new \
-key mohamed.key \
-out mohamed.csr \
-subj "/CN=mohamed/O=developers"
```

Résultat :

```
mohamed.csr
```

---

## Signification des champs

Le certificat contient des informations d'identité.

### CN (Common Name)

```
CN = mohamed
```

Kubernetes interprète cette valeur comme le **nom de l'utilisateur**.

L'utilisateur sera donc :

```
mohamed
```

---

### O (Organization)

```
O = developers
```

Kubernetes interprète cette valeur comme un **groupe**.

L'utilisateur appartiendra donc au groupe :

```
developers
```

Ainsi, après authentification, Kubernetes verra :

```
Utilisateur : mohamed

Groupes :
- developers
```

---

# Étape 3 – Signer le certificat

Le certificat doit être signé par la même autorité (CA) que le cluster Kubernetes.

## Vérifier la présence de la CA

Pour Minikube :

```bash
minikube ssh
```

Puis :

```bash
sudo ls /var/lib/minikube/certs
```

On doit retrouver notamment :

```
ca.crt
ca.key
```

Sur la machine hôte, les certificats sont généralement disponibles dans :

```
~/.minikube/
```

---

Signer ensuite la CSR :

```bash
openssl x509 \
-req \
-in mohamed.csr \
-CA ~/.minikube/ca.crt \
-CAkey ~/.minikube/ca.key \
-CAcreateserial \
-out mohamed.crt \
-days 365
```

Résultat :

```
mohamed.crt
```

---

# Étape 4 – Ajouter l'utilisateur dans le kubeconfig

Créer une nouvelle identité dans le fichier kubeconfig.

```bash
kubectl config set-credentials mohamed \
--client-certificate=mohamed.crt \
--client-key=mohamed.key
```

Vérifier :

```bash
kubectl config get-users
```

Résultat :

```
NAME
minikube
mohamed
```

---

# Étape 5 – Créer un contexte

Créer un contexte qui utilisera cet utilisateur.

```bash
kubectl config set-context mohamed-context \
--cluster=minikube \
--user=mohamed \
--namespace=rbac-demo
```

Vérifier :

```bash
kubectl config get-contexts
```

Exemple :

```
CURRENT   NAME               CLUSTER     AUTHINFO
*         minikube           minikube    minikube
          mohamed-context    minikube    mohamed
```

---

# Étape 6 – Utiliser ce contexte

Basculer sur ce nouvel utilisateur.

```bash
kubectl config use-context mohamed-context
```

Toutes les commandes `kubectl` seront désormais exécutées avec l'identité :

```
mohamed
```

---

# Étape 7 – Créer un Role

Créer le fichier `role.yaml`.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role

metadata:
  name: pod-reader
  namespace: rbac-demo

rules:
- apiGroups: [""]
  resources:
  - pods
  verbs:
  - get
  - list
  - watch
```

Appliquer :

```bash
kubectl apply -f role.yaml
```

---

# Étape 8 – Créer un RoleBinding

Créer le fichier `rolebinding.yaml`.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding

metadata:
  name: mohamed-binding
  namespace: rbac-demo

subjects:
- kind: User
  name: mohamed
  apiGroup: rbac.authorization.k8s.io

roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

Appliquer :

```bash
kubectl apply -f rolebinding.yaml
```

---

# Étape 9 – Tester les permissions

Avant le RoleBinding :

```bash
kubectl get pods
```

Résultat :

```
Error from server (Forbidden)
```

Après le RoleBinding :

```bash
kubectl get pods
```

Résultat :

```
NAME
nginx
redis
mysql
```

# Que fait Kubernetes lors de l'authentification ?

Lorsque l'utilisateur exécute :

```bash
kubectl get pods
```

Le processus est le suivant :

```text
Utilisateur
     │
     ▼
kubectl
     │
     ▼
Envoi du certificat
(mohamed.crt)
     │
     ▼
API Server
     │
     ▼
Vérifie la signature du certificat
     │
     ▼
Lit le certificat
     │
     ▼
CN = mohamed
O = developers
     │
     ▼
Utilisateur authentifié
     │
     ▼
Recherche des RoleBinding
     │
     ▼
Role associé
     │
     ▼
Autorisation RBAC
```

---

# Vérifier les permissions

Lister les permissions de l'utilisateur :

```bash
kubectl auth can-i --list --as=mohamed -n rbac-demo
```

Tester une permission :

```bash
kubectl auth can-i get pods --as=mohamed -n rbac-demo
```

Résultat attendu :

```
yes
```

Tester une action interdite :

```bash
kubectl auth can-i delete pods --as=mohamed -n rbac-demo
```

Résultat :

```
no
```

# Différence entre un utilisateur humain et un ServiceAccount

| Utilisateur humain | ServiceAccount |
|--------------------|----------------|
| Utilisé par une personne | Utilisé par une application |
| Authentification par certificat, OIDC, LDAP... | Authentification par token |
| Le certificat est stocké sur le poste de travail | Le token est monté automatiquement dans le Pod |
| Déclaré dans le kubeconfig | Associé au Pod via `serviceAccountName` |
| Sujet RBAC : `kind: User` | Sujet RBAC : `kind: ServiceAccount` |
| Exécute `kubectl` depuis le poste client | Exécute `kubectl` ou appelle l'API depuis un Pod |

---

# Conclusion

Un **utilisateur humain** n'est **pas créé dans Kubernetes**.

Kubernetes :

- authentifie l'utilisateur grâce à son certificat ;
- extrait son identité (`CN`) et ses groupes (`O`) ;
- applique ensuite les règles RBAC (`Role`, `ClusterRole`, `RoleBinding`, `ClusterRoleBinding`) pour autoriser ou refuser les actions demandées.

À l'inverse, un **ServiceAccount** est un objet Kubernetes créé dans un namespace et utilisé par les applications exécutées dans des Pods.
